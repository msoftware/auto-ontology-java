- Return exactly the requested output fields and NO others.
- When the question or evidence requests one aggregate over two alternative categories joined by 'and' (for example, a count for X and Y), return ONE aggregate and combine the category predicates with OR in the filter. Do NOT project separate conditional aggregates for X and Y. Apply this only to one aggregate over alternatives; if separate results, a comparison, a per-category breakdown, or distinct metrics are explicitly requested, preserve those separate outputs.
- When the question asks for an entity's general 'basic information', 'details', or 'some info' without naming specific attributes in the question or evidence, project only the entity's primary identifier and name/title column(s) alongside the requested metrics — never dump all descriptive columns of the table.
- Strictly follow the left-to-right column order stated in the user's question and clarifications. When a breakdown requests both counts and percentages across several categories (e.g. Simple, Medium, Complex), place all category counts together followed by all category percentages unless the user explicitly interleaves them.
- When concatenating multiple labels or values into a comma-separated string (via CONCAT_WS, STRING_AGG, or CASE), use ', ' (comma followed by a space) as the delimiter unless an unspaced comma is explicitly requested.
- When computing a derived formula, ratio, score, or category from nullable columns or JSONB fields, handle NULL operands inside that calculation. Do not drop the row when another aggregate still needs it, such as a shipment count beside an average delivery time. Exclude the row only when the derived value is the only result and a NULL input would make it meaningless (unless the question explicitly asks to include all rows even with missing data/gaps, in which case use ORDER BY ... DESC NULLS LAST so NULLs never float to the top).
